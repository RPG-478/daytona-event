# Nosana × Daytona で半日実装できるAIエージェント系ツール案

前提: Nosana に立てたオープンモデル(LLM)でコードや判断を生成し、Daytona のサンドボックスで実行・検証する。オーケストレーターは手元またはCloud Run上の小さなサービス(Go / TypeScript)。

## 結論(おすすめ順)

| 順位 | 案 | 半日での現実度 | この組み合わせである必然性 |
|---|---|---|---|
| 1 | テスト自動生成・修正ループ | 高 | 生成コードを実際に走らせて合否を返せる |
| 2 | モデル比較ハーネス | 高 | 複数モデルをGPUで並べ、同じ課題を隔離実行で採点できる |
| 3 | CSV分析エージェント | 高 | 任意コード実行が必要で、隔離が必須 |
| 4 | PR検証ボット | 中 | diffを当てた状態でテストを実行できる |
| 5 | README/ドキュメントのコード例検証 | 中 | 大量の小さな実行を使い捨て環境で回せる |
| 6 | k6シナリオ生成とドライラン | 中 | スクリプトの構文・動作を実行して確かめられる |
| 7 | バグ再現エージェント | 低〜中 | 再現スクリプトを試行錯誤で実行できる |

最初の1本は **案1** がおすすめ。ループの骨格がそのまま他の案に流用できる。

---

## 共通の骨格(全案で再利用、約2時間)

1. **Nosana**: vLLM か Ollama のコンテナをデプロイし、OpenAI互換のエンドポイントURLを得る
2. **Daytona**: APIキーを発行し、SDKでサンドボックスを作成・実行・削除できることを確認
3. **ループ本体**: 下の4関数だけ作る

```
generate(prompt)        -> code      # Nosana のエンドポイントを叩く
run(code | command)     -> result    # Daytona サンドボックスで実行
judge(result)           -> done?     # 終了条件(exit code、テスト合否など)
loop(task, maxIters=5)               # generate → run → judge を回す
```

守ること:

- APIキーはオーケストレーターだけに置き、サンドボックスには渡さない
- ループ回数とタイムアウトに上限を入れる
- サンドボックスは処理の最後に必ず削除する(自動停止の設定も併用)
- LLMの出力からコードブロックだけを抜き出す処理を最初に作る(ここで最も時間を失いやすい)

---

## 案1: テスト自動生成・修正ループ

- **入力**: 関数またはファイル1つ
- **出力**: 通るテストコードと、実行ログ
- **流れ**: 対象コードをサンドボックスに置く → LLMがテストを書く → 実行 → 失敗ログをLLMに戻して修正 → 通るまで最大5回
- **半日の範囲**: 単一ファイル、言語は1つ(Go の `go test` か Python の `pytest`)に固定
- **落とし穴**: テストが「通るだけ」の無意味な内容になる。アサーション数の下限をプロンプトで指定する
- **拡張**: カバレッジを計測して、未到達の分岐を次のプロンプトに渡す

## 案2: モデル比較ハーネス

- **入力**: コーディング課題10問程度(問題文と採点用テスト)
- **出力**: モデルごとの正答率・所要時間・トークン数の表
- **流れ**: Nosana に2〜3モデルをデプロイ → 各モデルに同じ課題を解かせる → 解答をサンドボックスで採点 → 集計
- **半日の範囲**: モデル2つ、課題10問、結果はCSV出力まで
- **落とし穴**: モデルごとに起動時間が違うので、全エンドポイントのヘルスチェックを通してから計測を始める
- **拡張**: 量子化や温度の違いを軸に追加する。自分のアプリ用のモデル選定にそのまま使える

## 案3: CSV分析エージェント

- **入力**: CSVファイルと自然言語の質問
- **出力**: 集計結果とグラフ画像
- **流れ**: CSVをサンドボックスにアップロード → LLMが pandas のコードを書く → 実行 → エラーなら修正 → 結果と画像を取り出す
- **半日の範囲**: CSV1ファイル、グラフは matplotlib の PNG 1枚
- **落とし穴**: LLMが列名を推測で書く。先頭数行と列の型をプロンプトに含める
- **拡張**: 複数ファイルの結合、定期実行してレポート化

## 案4: PR検証ボット

- **入力**: リポジトリURLとPR番号(またはdiff)
- **出力**: テスト結果の要約と、LLMによるレビューコメント
- **流れ**: サンドボックスでリポジトリをクローン → PRのブランチをチェックアウト → ビルドとテスト → ログとdiffをLLMに渡して要約
- **半日の範囲**: 公開リポジトリ1つ、結果は標準出力まで(GitHubへの投稿は後回し)
- **落とし穴**: 依存の取得に時間がかかる。依存を入れたスナップショットを先に作っておく
- **拡張**: GitHub Actions や Webhook から起動し、PRにコメントを自動投稿

## 案5: README/ドキュメントのコード例検証

- **入力**: Markdownファイル、またはドキュメントのURL一覧
- **出力**: 動かないコード例の一覧と、修正案
- **流れ**: コードブロックを抽出 → 1ブロックずつサンドボックスで実行 → 失敗したものだけLLMに原因と修正案を書かせる
- **半日の範囲**: 言語は1つ、単独で実行できるブロックのみ対象
- **落とし穴**: 断片的なコード(前のブロックに依存)が多い。同一ファイル内は連結して実行する方式にする
- **拡張**: CIに組み込み、ドキュメントの劣化を検知

## 案6: k6シナリオ生成とドライラン

- **入力**: APIの仕様(エンドポイント一覧、想定ユーザー数、性能要件)
- **出力**: k6スクリプトと、小規模実行の結果
- **流れ**: LLMが仕様からシナリオを導出してスクリプトを書く → サンドボックス内にモックAPIを立てる → 低負荷で `k6 run` → 構文エラーや閾値設定の不備をLLMに戻す
- **半日の範囲**: エンドポイント2〜3個、VU数は1桁、モックは固定レスポンス
- **落とし穴**: サンドボックスから本番や外部への負荷は掛けない(規約と安全の両面)。あくまでスクリプトの検証用
- **拡張**: 仕様→シナリオの導出過程をLLMに説明させ、教材として使う

## 案7: バグ再現エージェント

- **入力**: Issueの本文とリポジトリURL
- **出力**: バグを再現する最小スクリプトと、再現時のログ
- **流れ**: クローン → LLMが再現スクリプトを書く → 実行 → 期待したエラーが出るまで修正
- **半日の範囲**: 再現条件が明確なIssue数件で試す
- **落とし穴**: 「再現した」の判定が難しい。Issueのエラーメッセージとの文字列一致を終了条件にする
- **拡張**: 再現後に修正パッチの生成まで進める

## 半日の時間配分(案1の場合)

| 時間 | 作業 |
|---|---|
| 0:00–0:45 | Nosana にモデルをデプロイ、curlで応答確認 |
| 0:45–1:15 | Daytona のキー発行、サンドボックスで Hello World |
| 1:15–2:15 | 共通の骨格(generate / run / judge / loop) |
| 2:15–3:30 | 案1の固有部分(ファイル配置、テスト実行、失敗ログの整形) |
| 3:30–4:00 | 上限・タイムアウト・後始末、簡単なサンプルで通し確認 |

## 始める前に確認すること

- Nosana のクレジット残高と、使うGPUマーケットの単価
- 使うモデルがそのGPUのVRAMに収まるか(収まらないと起動で止まる)
- Daytona サンドボックスの外部通信の制限(パッケージ取得やクローンが通るか)
- Daytona のリージョンと、日本からの往復遅延
