# 担当別タスク：DSH × Daytona × Nosana

> DSH は **DeepSeek Harness** を指す前提。既存の [構成図](../ARCHITECTURE.md) に対し、ハーネスには DSH を利用する。接続方式は実機確認後に決める。

## 作るもの

対象コードを渡すと、Nosana 上のモデルを使ってテストを作成し、Daytona 上で実行する。失敗した場合はログをもとに修正し、結果を画面に表示する。

**まず確認すること**: Daytona 上で DSH を起動できるか、DSH から Nosana の OpenAI 互換エンドポイントに接続できるか。モデルの応答だけでなく、必要なツール呼び出しまで小さな例で確認する。未確認の接続を完成済みとして扱わない。

## Daytona 担当（1人）

**役割**: DSH と生成したテストを動かすサンドボックスを用意する。

- [ ] Daytona のサンドボックスを作成し、選んだ言語のテストを実行できる環境を用意する
- [ ] DSH をセットアップし、サンドボックス内で小さなタスクが動くか確認する
- [ ] Nosana の URL への接続を確認し、モデル・認証情報の設定方法をオーケストレーター担当と共有する
- [ ] 対象ファイルの配置、テストの実行、ログ・終了状態の取得方法を決める
- [ ] タイムアウトと、成功・失敗時のサンドボックス停止／削除を確認する
- [ ] セットアップ手順と必要な環境変数名を共有する

**渡すもの**: 接続・起動手順、必要な環境変数名、実行環境とログ取得方法。

## オーケストレーター担当 A（1人）：DSH・モデル連携

**役割**: DSH を使って Nosana のモデルにテスト生成・修正を依頼する。

- [ ] Nosana 担当から URL、モデル ID、認証方法を受け取り、DSH の接続設定を試す
- [ ] 単一ファイルを対象に、テスト生成の指示と実行手順を用意する
- [ ] テスト失敗時にログを渡して修正できるか確認する
- [ ] DSH が担う生成・ツール実行・修正の流れを確認し、独自に作る制御部分との境界を決める
- [ ] テスト未検出、モデル応答エラー、実行失敗を成功と区別する
- [ ] 試行回数・時間の上限と、結果・ログの受け渡し形式を担当 B と決める

**渡すもの**: DSH の起動・設定方法、プロンプト、結果とエラーの受け渡し方法。

## オーケストレーター担当 B（1人）：起動・状態管理・Web UI

**役割**: ユーザーから実行を受け付け、処理の状態と結果を見せる。

- [ ] 対象コードを入力し、実行を開始する最小 Web UI を作る
- [ ] Daytona 担当・担当 A と、DSH の起動方法と結果の受け渡しをつなぐ
- [ ] 実行中・成功・失敗・タイムアウトを表示する
- [ ] 生成されたテストと実行ログを確認できるようにする
- [ ] 処理の上限と終了時の後始末を、DSH／Daytona 側の機能と重複しない形でつなぐ
- [ ] サンプルで通し確認し、実行手順とデモ手順をまとめる

**渡すもの**: Web UI、実行手順、デモ用サンプル。

## 3人で合わせること

- [ ] 言語、テストコマンド、対象ファイル形式、デモ用サンプルを決める
- [ ] Nosana の URL・モデル ID・認証方法と、DSH のツール呼び出し対応を確認する
- [ ] 接続できない間はモックを使い、実接続後に1件通す
- [ ] API キーはチャットやリポジトリに貼らず、必要な実行環境へ安全に渡す。DSH を Daytona 内で動かす場合は、Nosana 接続に必要な認証情報だけを渡し、ログや成果物に含めない
- [ ] 正常終了、テスト失敗、タイムアウトを確認し、使い終わったサンドボックスを片付ける

## 完了イメージ

Web UI からコードを渡すと、DSH と Nosana によるテスト生成、Daytona での実行、必要に応じた修正が進み、最終状態とログを確認できる。DSH／Nosana／Daytona の実接続で少なくとも1件を通す。
