## 目的と対象

Nosana のモデルによるコード生成、Daytona での実行、結果の判定をつなぎ、上限付きの自動ループとして動かす。実装案と言語はチームで決定する。未決定の間は、`idea_genki/idea.md` の推奨案である「単一ファイルのテスト自動生成・修正」を仮の対象にし、モックで先に接続部分を作る。

このタスクは推論モデルとサンドボックスを組み合わせる案向け。学習ジョブを扱う AT Studio 案を採用する場合は、役割と入出力をチームで見直す。

## 他担当との受け渡し

| 相手 | 受け取るもの | 確認すること |
|---|---|---|
| Nosana 担当 | サービス URL、モデル ID、認証方法、接続確認手順 | OpenAI 互換のチャット API の応答、利用可能なタイムアウト |
| Daytona 担当 | API キーの受け渡し方法、サンドボックス作成・実行・削除手順、必要ならスナップショット名 | 選択言語の実行環境、ファイル配置、終了コードとログの取得方法 |

- [ ] 実装言語、テスト実行コマンド、入力形式、デモ対象をチームで決める
- [ ] API キーは環境変数などで受け取り、リポジトリ・チャット・ログに記載しない
- [ ] 待ち時間に備えて Nosana / Daytona のモックを使えるようにする

## 実装タスク

### 1. 入出力と準備

- [ ] 1つの対象ファイルと、必要な指示を受け取る入口を作る
- [ ] 結果に最終状態、試行回数、生成コード、実行ログ、失敗理由を含める
- [ ] 試行上限（初期値 5）、各処理のタイムアウト、モデル設定を変更できるようにする
- [ ] デモで使う対象コードと、期待するテスト内容を用意する

### 2. generate — 生成

- [ ] 対象コードとテスト生成指示を Nosana のチャット API に送る
- [ ] 応答からコードブロックを抽出する。コードがない・複数候補があるなど曖昧な応答は成功扱いにせず、理由を返す
- [ ] 2回目以降は前回の生成コードと失敗ログを渡し、修正を依頼する
- [ ] 空応答、API エラー、タイムアウトを区別して記録する

### 3. run — 実行

- [ ] Daytona サンドボックスを作成し、対象コードと生成したテストをファイルとして配置する
- [ ] 決めたテストコマンドを実行し、終了コード、標準出力、標準エラー、タイムアウトを回収する
- [ ] 実行コマンド・ファイル配置・依存関係は選択した言語に合わせて固定する
- [ ] 成功・失敗・タイムアウトのいずれでもサンドボックスを削除する。削除失敗は記録し、必要なら手動で後始末する
- [ ] オーケストレーターの API キーを生成コードやサンドボックスへ渡さない

### 4. judge / loop — 判定と再試行

- [ ] テスト実行の終了コードと実行結果に基づき成功・失敗を判定する。テストが検出されない場合は成功にしない
- [ ] 生成 → 実行 → 判定を繰り返し、成功時または試行上限・タイムアウト・回復不能なエラーで終了する
- [ ] 各試行の番号、判定、ログを残し、最終結果と区別する
- [ ] 修正用にモデルへ渡すログの長さを制限し、秘密情報が含まれないようにする
- [ ] テストが通ることだけでは品質を保証できないため、デモではアサーションの内容も確認する

## 結合・確認

- [ ] モックで「初回成功」「失敗後に修正して成功」「上限到達」を確認する
- [ ] 空応答または API エラー、実行タイムアウト、後始末を確認する
- [ ] 実際の Nosana と Daytona を接続し、少なくとも1タスクを完走する
- [ ] サンプル3件で結果とテスト内容を確認し、失敗した場合も原因を記録する
- [ ] 実行方法、必要な環境変数名、サンプル、既知の制限を README 等に記載する
- [ ] デモ用に実行ログを準備し、実動作とモック・過去の記録を明確に区別する

## 完了条件

- 課題を入力すると、生成 → Daytona での実行 → 判定が自動で進み、成功または停止理由が確認できる。
- 試行回数とタイムアウトに上限があり、終了時にサンドボックスの削除を試みる。
- チームの別メンバーが手順とサンプルを使って実行できる。

**全員に渡すもの**: 実行手順、必要な環境変数名、デモ用サンプル、確認済みの結果と制限。
